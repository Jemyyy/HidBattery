# HidBattery

Windows 10/11 上的无线外设电量小工具：托盘图标直接显示电量数字，另有简洁面板与完整调试界面。

零第三方依赖 —— 只用 Python 标准库 + `ctypes` 直接调用 Windows DLL，不依赖 `hidapi` / `pysystray` / `Pillow` / `pywin32`。

## 支持的设备

| 设备 | VID:PID | 通道 |
|---|---|---|
| 黑爵 AK992 三模 RGB 键盘（有线） | `320F:50C2` | UP `0xFF1C` / Usage `0x0092`，64 字节 in/out |
| 黑爵 AK992 三模 RGB 键盘（2.4G 接收器） | `320F:50C3` | 同上，两种连接方式协议完全一致 |
| 黑爵 AJ179 双模鼠标 | `249A:5C2F` | UP `0x0001`，33 字节 in/out |

协议参数写死在 [devices.py](devices.py) 的 `DEFAULT_PROTOCOLS` 中，可在调试界面里手动标定，标定结果存入 `%APPDATA%\HidBattery\config.json`。

## 环境要求

- Windows 10 / 11（x64）
- Python 3.10 及以上（用到 `X | None` 类型写法）
- 无需管理员权限；只有「创建桌面符号链接」在未开启开发者模式时会降级

## 快速开始

```powershell
# 只读一次，打印两行电量（最常见的自检方式）
python my_devices.py --once

# 托盘常驻（默认形态）
pythonw my_devices.py --tray

# 只开简洁面板
pythonw my_devices.py --panel

# 完整调试版：枚举 HID、转储 Feature Report、手动标定协议
python my_devices.py --debugui
```

首次使用时注册开机自启与桌面入口：

```powershell
python my_devices.py --setup    # 创建启动文件夹快捷方式 + 桌面链接
python my_devices.py --status   # 复查两者状态
```

## 命令行参数

| 参数 | 说明 |
|---|---|
| `--once` | 只读一次并打印两行电量 |
| `--tray` | 托盘常驻（默认形态） |
| `--panel` | 只打开简洁面板 |
| `--debugui` | 完整调试版界面 |
| `--setup` | 创建自启快捷方式与桌面链接 |
| `--status` | 查看自启与桌面链接状态 |
| `--interval N` | 刷新间隔秒数，30 ~ 1800，默认 60 |
| `--debug` | 输出控制台调试信息（**不写任何日志文件**） |
| `--exit-after N` | 冒烟测试用：运行 N 秒后自动优雅退出 |

## 托盘交互

- **右键**：打开 / 前置简洁面板（已打开则不重复创建）
- **左键**：立即刷新一次
- **悬停**：tooltip 显示「设备名：电量（更新时间）」
- 第二个实例不会重复起托盘，而是唤醒已有实例并打开面板（单实例互斥体保护）

面板卡片颜色：≥60% 绿，30–59% 黄，<30% 红，读不到时灰。

## 项目结构

| 文件 | 职责 |

| `debugui.py` | 调试版界面（设备枚举 / Feature Report 转储 / 白名单命令发送） |
| `sysinteg.py` | 开机自启 `.lnk`、桌面符号链接 / junction / 硬链接降级 |

## 已知限制

- 键盘 2.4G 链路**空闲后会休眠并拒绝应答**。工具每 5 秒发一次保活帧维持唤醒；但若链路已经睡了，任何主机侧帧都唤不醒它，需按一下键盘任意键。
- 键盘第 9 字节与「连接方式」同时变化，无法区分「充电」与「已连线」，因此界面只显示电量，不显示充电状态。
- 只适配上述两款设备，其他外设需在 `devices.py` 中补充协议。

# 构建时容易犯的错误

以下全部是本项目开发中真实踩过并已修复的坑，按「症状 → 原因 → 正确做法」列出。

## 一、HID 通道与协议

### 1. 用 `HidD_SetOutputReport` 写厂商通道，数据根本没到设备

- **症状**：`HidD_SetOutputReport` 返回 `True`，设备毫无反应，等待超时。极易误判为「设备不应答 / 必须装官方驱动」。
- **原因**：该 API 在 AK992 的厂商接口上是**静默空转** —— Windows 报告成功，数据从未进入 OUT 中断管道。
- **正确做法**：对文件句柄直接 `WriteFile` 写 OUT 管道（`write_output`）。判定方法：看设备是否把写入**原样回显**；`WriteFile` 能立刻收到回显，`HidD_SetOutputReport` 3 秒内一帧都没有。

### 2. 把固件的「原样回显」当成应答

- **症状**：电量恒为 0，或读到明显无意义的数值。
- **原因**：AK992 固件对**未知命令**会原样回显请求帧；若只按宽松前缀匹配，就会把回显当应答解码。
- **正确做法**：丢弃与请求帧完全相同的帧，并要求应答前缀严格匹配 `04 20 00 1A 06`。

### 3. 休眠链路回的失败帧被解成「假 0%」

- **症状**：键盘突然显示 0%，但实际有电。
- **原因**：链路休眠时设备回 `04 20 00 **FF** 06 ...`（第 3 字节由 `0x1A` 变 `0xFF`）。若 `match_prefix` 只写 `[0x04, 0x20]`，这一帧会被当成正常应答，第 8 字节恰好是 0。
- **正确做法**：`match_prefix` 必须包含命令字节（`[0x04, 0x20, 0x00, 0x1A, 0x06]`），失败帧直接丢弃并报「设备可能已休眠」。

### 4. 认为「官方驱动必需」，其实是驱动在喂链路

- **症状**：驱动开着就能读，关掉几分钟后全失败。
- **原因**：官方驱动每 ~4.9 秒发一次同样的 `04 20 00 1A 06` 查询帧（另有 ~1.9 秒一次心跳），把 2.4G 链路一直维持在唤醒态。杀掉驱动后立刻连测几次仍成功，是因为链路还没睡——这是**假阳性**。
- **正确做法**：工具自己做 5 秒周期的保活帧，不必依赖官方驱动进程。验证结论时要先让链路空闲足够久再测。

### 5. 误以为「能用」就可以放松校验

- **症状**：偶发读到 0% 或跳到异常值。
- **原因**：休眠/半唤醒状态下的帧既不是回显，也不是有效应答。
- **正确做法**：解码前校验命令字节、长度与数值范围（0–100），任一不符即判失败，宁可显示「读取失败」也不要显示假数据。

### 6. 64 字节通道忘了 Report ID `0x04`

- **症状**：`WriteFile` 返回 `ERROR_INVALID_PARAMETER`（87）。
- **原因**：该接口要求帧首字节为 Report ID `0x04`，长度必须 64。
- **正确做法**：`request_frame` 首字节固定 `0x04`，并补零到 `frame_len = 64`。

### 7. 试图写 33 字节的 IF5 通道

- **症状**：`set_output_report` 与 `write_output` 都返回 `False`。
- **原因**：键盘的 IF5（33 字节）通道不可写，只能读。
- **正确做法**：厂商命令只写 IF4（64 字节）。

### 8. 拿 `HidD_SetOutputReport` 的返回值当「已送达」的证据

- **症状**：调试界面显示「发送成功」，设备无任何变化。
- **原因**：同上，返回值不代表数据到达。
- **正确做法**：发送后必须读回显或用设备状态验证。

## 二、ctypes 与 Win32 细节

### 9. `SetupDiGetDeviceInterfaceDetailW` 的 `cbSize` 写 6

- **症状**：枚举接口失败或拿到野指针。
- **原因**：x64 下 `SP_DEVICE_INTERFACE_DETAIL_DATA_W` 的 `cbSize` 需 4 字节对齐成 8。
- **正确做法**：按指针宽度算 `6 if 32 位 else 8`。

### 10. `HIDP_VALUE_CAPS` 的字段名与实际布局不符

- **症状**：`'HIDP_VALUE_CAPS' object has no attribute 'UsagePage'`。
- **原因**：该结构首字段在源码里叫 `Usage`，实为 `UsagePage`（union 的 `UsageMin/UsageMax` 未实现）。
- **正确做法**：用 `vc.Usage` 当用法页读；需要 union 其他成员时要自己补结构。

### 11. `overlapped` 句柄配同步 `WriteFile`

- **症状**：写入报 87。
- **原因**：用 `FILE_FLAG_OVERLAPPED` 打开的句柄必须走异步 `WriteFile` + `OVERLAPPED`；同步调用非法。
- **正确做法**：读用 `overlapped=True` 的句柄，写用普通（同步）句柄；本项目即按此拆分。

### 12. 自己拼 `IShellLink` vtable 下标照抄头文件顺序

- **症状**：创建 `.lnk` 时访问冲突（崩溃）。
- **原因**：`IShellLinkW` 的真实 vtable 下标与头文件里的逻辑顺序不一致。
- **正确做法**：实测标定后的下标为 `QueryInterface=0`、`Release=2`、`Save=6`、`SetDescription=7`、`SetWorkingDirectory=9`、`SetArguments=11`、`SetIconLocation=17`、`SetPath=20`；`3/21/23/25` 会导致崩溃。改动前先用隔离进程逐个验证。

### 13. `Shell_NotifyIconW` 的图标用了低分辨率位图

- **症状**：托盘数字模糊、发虚。
- **原因**：16×16 直接绘制，GDI 抗锯齿不足。
- **正确做法**：4× 超采样绘制后降采样生成 alpha，再用 `CreateIconIndirect` 建图标；洋红 `FF00FF` 作 key 色剔除背景。

## 三、tkinter / GUI

### 14. `tkinter` 没有 `Combobox`

- **症状**：界面启动即崩。
- **原因**：`Combobox` 属于 `tkinter.ttk`，`tkinter` 本体没有。
- **正确做法**：`from tkinter import ttk`，用 `ttk.Combobox`。

### 15. 在 UI 线程里同步读设备

- **症状**：点刷新时界面卡死、无响应。
- **原因**：HID 读取最长要等数百毫秒到 1 秒。
- **正确做法**：读取放后台线程，UI 线程只通过 `queue.Queue` + `after()` 泵取结果。

### 16. 用 `sleep` 循环做定时刷新

- **症状**：空闲 CPU 占用高，或刷新不准。
- **原因**：忙等 / 阻塞线程。
- **正确做法**：托盘用 `SetTimer`（`WM_TIMER`），面板用 `root.after()`；没有任何 sleep 轮询。

## 四、系统集成

### 17. 用注册表 `Run` 做开机自启

- **症状**：任务管理器「启动」标签里看不到，用户无法禁用。
- **原因**：`Run` 键不进入启动项管理列表。
- **正确做法**：在「启动」文件夹放 `.lnk`（本项目 `--setup` 自动创建）。

### 18. `.lnk` 目标写成 `python.exe` 或相对路径

- **症状**：开机弹黑色控制台窗口，或快捷方式失效。
- **原因**：`python.exe` 会附带控制台；`.py` 无文件关联时相对路径解析失败。
- **正确做法**：目标固定为 `pythonw.exe` 的**绝对路径**，参数为脚本绝对路径。

### 19. 桌面入口做成副本

- **症状**：改了项目里的脚本，桌面那份不生效。
- **原因**：复制文件而非链接。
- **正确做法**：目录链接优先 `os.symlink`（需开发者模式/管理员），失败降级 `mklink /J`（junction）；文件链接失败再降级 `os.link`（硬链接）。

### 20. 没有单实例保护

- **症状**：托盘出现 4 个图标（两台设备 × 两个实例），读数互相干扰。
- **原因**：多个实例同时运行，各自 `Shell_NotifyIconW`，且并发抢同一 HID 设备。
- **正确做法**：命名互斥体 `CreateMutexW("Local\...")`，检测 `ERROR_ALREADY_EXISTS` 后向已有实例发消息唤醒，而不是新建。

### 21. 退出时不删托盘图标

- **症状**：进程没了，通知区域残留幽灵图标。
- **原因**：未调用 `NIM_DELETE`，或消息循环未正常退出。
- **正确做法**：退出路径必须先 `Shell_NotifyIconW(NIM_DELETE)`，再 `DestroyWindow` / `PostQuitMessage`；还要处理 `TaskbarCreated`（explorer 重启后重新注册）。

### 22. 提权启动的进程变成杀不掉的僵尸

- **症状**：普通权限 `taskkill` 无效，进程仍占着设备。
- **原因**：以管理员身份启动的进程，普通权限无法终止。
- **正确做法**：同样用提权 `taskkill /F /PID` 清理；调试时尽量避免不必要的提权。

## 五、性能与验收

### 23. 每 5 秒做一次全机 HID 枚举

- **症状**：空闲 CPU 明显超标（一次枚举约 0.1 秒 CPU）。
- **原因**：保活只写一帧，却在每次调用时重新枚举全部接口。
- **正确做法**：缓存设备路径，只有缓存缺失或写失败（换接口/换连接方式）时才重新枚举。本项目实测 75 秒空闲 0.2 秒 CPU。

### 24. 写日志文件

- **症状**：违反「不产生日志」的验收项。
- **正确做法**：只有传 `--debug` 时才往控制台打印，任何情况下不落盘。

## 六、验证方法论

### 25. 用「刚杀驱动时连测几次都成功」证明脱驱动

- **症状**：得出错误结论，几小时后被现实推翻。
- **原因**：链路还醒着，属于**假阳性**。
- **正确做法**：验证「不需要官方驱动」必须让链路空闲足够久（数分钟）再测，或先让键盘睡眠再测。

### 26. 只看导入表的一两个函数就下结论

- **症状**：对驱动走的通道判断错误。
- **正确做法**：静态解析 PE 导入表，检查是否出现 `HidD_SetOutputReport` / `HidD_SetFeature` / `DeviceIoControl` / `WinUsb_*`，这比反复黑盒试验快得多。
